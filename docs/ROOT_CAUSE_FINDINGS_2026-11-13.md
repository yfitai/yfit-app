Anonymous observation of the app callback at 14:35:57 and 14:36:32 EST found a blank page and empty React root. Independent GET-only checks returned HTTP 200 `text/html` for `/auth/assets/index-DPUm8UCb.js`, but HTTP 200 `application/javascript` for `/assets/index-DPUm8UCb.js`. This failure happens before React and Supabase initialize; it is not evidence that Supabase rejected a valid session. A web repair must preserve the separate relative-base requirement for Capacitor rather than changing both targets indiscriminately.

**The deployed signup entry also opens the wrong tab.** Anonymous app `/signup` observation at 14:33:58 EST and www `/signup` observation at 14:34:31 EST showed login, not account creation. These are source-confirmed control-flow problems, not proof of a completed production Google return or a deployed profile-policy denial.

**Profile work can prevent authentication helpers from completing, and other failures are silently discarded.** Email login/signup helpers at `src/lib/supabase.js:58–98,127–142` await noncritical profile work without a local bound. Unsettled mocked profile reads and inserts prevented helper completion in the offline diagnostic. `InstallGuide.jsx:124–138` ignores upsert errors before dismissal/completion, and Goals does not implement the missing-profile creation claimed by the helper. `App.jsx:194–224,334–341` ignores a resolved `getSession` error and has no active callback-error display path. ## Paid access, checkout and fulfillment

**Expired trial and grace states incorrectly retain Pro access in the deployed client.** The entitlement expression in `SubscriptionContext.jsx:97–124`, used by active `ProRoute.jsx:39,51–52`, grants Pro for an expired paid-plan trial or expired grace even when `isTrialing=false`. The actual public asset expression was evaluated with synthetic states, so this is deployment-evidenced logic, not merely a local-source finding. No affected real account was identified. An active recurring subscription's `current_period_end` alone is not sufficient to declare access expired; authoritative subscription policy must decide that case.

**The active checkout return points to a missing route.** `UpgradeModal.jsx:121` and `create-checkout-session.js:43` return to `/payment-success`, but that route is absent from both source and deployed route tables (`App.jsx:325–342,355–405`). `PaymentSuccess.tsx` is dormant and not imported by the active router. Its wording must therefore not be described as an observed deployed misleading success screen. Public GETs to the three Stripe API paths—create-checkout-session, create-portal-session and webhook—returned HTTP 405, establishing route presence only. They do not establish successful checkout, webhook health or parity with the checked-in server revision; no POST was performed.

**The server-source payment gates fail independently of price-variable alignment.** At `webhook.js:98–136`, recurring `trialing`, `incomplete` and `past_due` subscriptions are forced to active, and unpaid correctly mapped one-time sessions can receive lifetime access. Unknown price mapping defaults to monthly at `webhook.js:34–35`, while payment mode overrides mapping to lifetime at `118–136`. The checked-in status CHECK at `subscription_schema.sql:18–19` also conflicts with Stripe statuses passed through at `webhook.js:155`. Offline tests used aligned synthetic prices, so these reproduced defects are not explained away by a possible environment-variable mismatch. They remain server-source findings because the deployed server revision and configuration were not established.

**Purchase binding and event handling are not sufficiently authoritative or durable in source.** `create-checkout-session.js:26,43–60` and `webhook.js:85–91,258–271` bind purchases through caller-supplied email rather than immutable verified user identity. Transient lookup errors are acknowledged with HTTP 200 without a durable receipt. Successful-invoice updates that affect zero rows are also acknowledged (`webhook.js:172–189`), and an old subscription deletion can downgrade lifetime access (`228–248`). No persisted event/session ledger or current-subscription guard was found. Public Payment Links are not inherently defective; the identified problem is missing durable identity claim and reconciliation. Signature verification and yesterday's byte-split finding were not rerun unchanged, and today's diagnostic explicitly stubs signature verification.

**Checked-in subscription policies create a serious permission concern, but live exploitability is unverified.** `subscription_schema.sql:75–81` permits unrestricted owner INSERT and PUBLIC UPDATE with `USING(true)`, subject to actual grants and any restrictive policies. The portal trusts stored customer linkage at `create-portal-session.js:52–60,113–116`. Deployed schema, grants and RLS parity remain unknown. The prepared [catalog-only read-only SQL](/home/ubuntu/yfit-app-full/scripts/diagnostics/payments.readonly.sql) was not executed; it is an authorization-dependent inspection aid, not a migration or proposed permission change.

**Production Stripe configuration remains unresolved, and lack of charges is not a defect.** Checkout and webhook use different price-variable families (`create-checkout-session.js:8–12` versus `webhook.js:23–29`), but an actual mismatch is not confirmed because both families may be configured. Yesterday's catalog, subscription and webhook reads returned 403; unchanged denied calls were not repeated. Product currency, trial settings, delayed-method enablement, endpoint registration/signing/API version and delivery health remain unknown. No charges since August is not evidence of a payment bug and was not retested. Currency or tax migration is not justified by these findings.
